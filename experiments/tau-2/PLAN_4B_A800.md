# TAU-2: 4B student + AReaL teacher trajectories, experiment plan (A800)

Starting 2026-10-27. Conclusions from the previous phase (Phase 0/1, student Qwen3.5-2B, teacher Qwen3.8-27B) are in improvement plan v3:
none of the 13 configurations that transferred 27B ability to 2B significantly beat base; we also measured that 4B alone is about 10 points above 2B,
and already ties 27B. So this phase switches to **a 4B student + ready-made trajectories from a stronger teacher**.

## Fixed conventions

- Split: `experiments/tau-2/data/partition_v2.json` (TRAIN 139 / VAL 67 / EVAL 67), unchanged.
- Train only on TRAIN and on synthetic data that does not overlap official tasks. Telecom dialogues in the AReaL data carry official `task_id`s;
  any dialogue belonging to VAL/EVAL is dropped entirely (`scripts/areal_to_tokens.py`, 9 dialogues dropped).
- Model selection and tuning use only the frontier training tasks and VAL; EVAL is reported only once, at the end.
- Each results directory corresponds to exactly one configuration; before evaluation, confirm the adapter is actually in effect (logprobs differ from base).
- Data, models, and dependencies are all downloaded on the data platform from domestic mirrors (ModelScope / hf-mirror / Aliyun PyPI /
  official PyTorch index), then rsynced to the A800 shared storage `/public/home/ai_user_2/mera4b`.

## Reference numbers (measured on 5090, local 4B user simulator, seed 300, 4 trials per task)

| Model | VAL pass^1 | frontier training tasks (58 tasks × 8 trials) |
|---|---|---|
| Qwen3.5-2B | 23.5% | 45.0% |
| Qwen3.5-4B | 34.0% | 58.2% |
| Qwen3.8-27B (answers every turn) | 31.7% | 59.3% |

The minimum detectable difference for a single VAL run is about 10 points; merging two seeds (8 trials) gives about 7 points. The frontier training tasks are more sensitive
and are used to judge "whether training was learned"; VAL is used to judge generalization.

## Data

- `inclusionAI/AReaL-tau2-data` (Apache-2.0, ModelScope): SFT has 33,531 per-turn samples from 2,499 dialogues;
  RL has 1,982 synthetic tasks and 9 database snapshots.
- After conversion: 1,983 successful dialogues (retail 992 / airline 824 / telecom 167), about 21.7M tokens;
  the system prompt and tool definitions are regenerated by tau2 on the data platform and are byte-identical to the evaluation side (hashes checked);
  thinking content is discarded (student evaluation runs without thinking), only assistant turns are trained, and tau2's fixed opening line is not trained.
- Note: the dialogues were generated by Claude (tool call ids are `toolu_bdrk_*`). Research use only; publishing a model externally requires separately confirming the terms.

## Steps

### S0 Environment and smoke test (A800, about 1 hour)

What: build the training environment with Python 3.12 + torch 2.7.1+cu118 + transformers 5.10.4 + peft + fla 0.5.2
(in October this ran Qwen3.8-27B LoRA on the same machine model); run 4B LoRA for 4 steps.

Expected: `torch.cuda.is_available()` is true; fla's GDN kernels compile; the 4-step loss is finite and decreasing.

If not:
- CUDA unavailable: driver 515 only supports up to CUDA 11.7; confirm the cu118 wheel is used and relies on CUDA minor-version compatibility;
  if it still fails, switch to torch 2.6+cu118.
- fla/Triton errors: apply the October fixes, set `TRITON_PTXAS_PATH=/usr/local/cuda/bin/ptxas` and
  a separate Triton cache directory per process; if it still fails, use the GDN torch implementation bundled with transformers (slow but works).
- Memory or logits too large: chunked cross-entropy (already in the training script); lower the per-sequence cap (currently 32k tokens).

### S1 Evaluation path (in parallel with S2, half a day)

Problem: evaluation needs vLLM to serve Qwen3.5, and a vLLM that supports Qwen3.5 needs CUDA 12 or later, while the A800 driver is 515.

Approach (in priority order):
1. Try CUDA forward compatibility on the A800 (cuda-compat user-space libraries + CUDA 12.8 builds of torch/vLLM).
2. If that fails: transfer the trained adapter (a few hundred MB) to the 5090 (jdc) and evaluate with the existing evaluation pipeline (need to confirm transfer out is allowed).
3. If neither works: on the A800, start a simple OpenAI-compatible server with transformers for evaluation (slow, frontier subset only).

Expected: at least one path works, and evaluation results are comparable to the 4B base numbers on the 5090 (same user simulator, same seed).

### S2 4B LoRA SFT on AReaL dialogues (A800, about half a day)

What: two groups in parallel, 4 GPUs each; LoRA rank 64, alpha 128, covering all linear layers; 2 epochs per group,
saving an adapter every epoch.
- A: lr 1e-4
- B: lr 3e-5

Evaluation: test each adapter on the frontier training tasks and VAL (seed 300); add seed 1300 for the best one.

Expected (bar to pass): frontier training tasks ≥ 5 points above 4B base with the 95% CI lower bound > 0; VAL not below base,
ideally significantly higher.

If not:
- Training loss not decreasing or NaN: check the label mask (decode randomly sampled training tokens); lower lr by one step.
- Frontier drops (repeating the 2B collapse): first look at behavior statistics: repeated tool calls, fraction hitting the step limit, dialogue length.
  - More repeated calls: lower lr to 1e-5, or train only 1 epoch.
  - Dialogues noticeably longer (learned the teacher's lengthy confirmations): align the evaluation step limit with the training data, or filter overly long dialogues.
  - All normal but still dropping: the AReaL synthetic databases differ in distribution from the official databases; add replay of the student's own
    successful trajectories on TRAIN (1 per task).
- Frontier rises but VAL does not move: first add the second seed; then break down by domain. If only airline/retail rise
  and telecom does not move, telecom data is too small (167 dialogues); oversample telecom 3x and train another group.
- Both groups show only small 1–3 point gains: data volume is the bottleneck; move to S3 and continue training with the RL tasks.

### S3 GRPO (after S2 passes, 1–2 days)

What: on the best S2 adapter, run GRPO on AReaL's 1,982 RL tasks (each task loads its own database),
with reward from the official tau2 judgment only. The environment first needs "per-task database loading" (`db_path`).

Prerequisite: S1 path 1 works (VERL needs vLLM for rollout). Otherwise run on the 5090 with LoRA, 16k context,
batch 4 (2B OOMed at batch 8; 4B needs to be more conservative).

Expected: training reward rises; frontier training tasks and VAL keep improving over S2.

If not:
- Reward not rising, model barely moving: too many tasks with zero within-group GRPO variance; first sample the S2 model 8 times on the RL tasks
  and keep only tasks that are sometimes right and sometimes wrong.
- Reward rises but evaluation drops: the synthetic training databases are inconsistent with the official distribution; mix in official TRAIN tasks (our 139 tasks).
- OOM: reduce batch and response length, enable gradient checkpointing.

### S4 Final evaluation

On EVAL, use a hosted model as the user simulator (needs an API key), and report pass^1 / pass^4 and 95% CI for 4B base, S2, and S3.
Until the key is available, all comparisons use the local 4B user simulator, and this is noted.
